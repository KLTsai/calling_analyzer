# LLM Gateway 用量記錄分析工具

筆試題 6 的實作。讀取 Gateway 的 JSON Lines 呼叫記錄，輸出一份報表，回答三個問題：**錢花在哪個部門、多少錢是白花的、哪裡不對勁**。只用 Python 標準庫，不需要安裝任何套件。

## 快速開始

需要 Python 3.11+。有 [uv](https://docs.astral.sh/uv/) 的話會自動取得合適的 Python：

```bash
uv run analyzer.py sample_data.jsonl                          # 範例資料（2,000 筆）的報表
uv run --with "pytest>=8,<9" pytest                           # 101 個測試
uv run generate.py --seed 99 | uv run analyzer.py /dev/stdin  # 換一份隨機資料
```

沒有 uv 就把 `uv run` 換成 `python3`（測試需要自行安裝 pytest）。其他選項：`--json` 輸出機器可讀格式，`--include-users` 輸出逐人明細（預設關閉），`--min-samples N` 調整錯誤率的樣本門檻。

## 題目要求與我的判斷

| 題目要求 | 報表區塊 | 判斷 |
|---|---|---|
| 1. 各部門費用、無法歸屬比例 | 部門費用 | 無法歸屬再用 `agent_id` 拆成三種，因為負責的人不同：直接呼叫（結構性，分不出來）、Agent 沒帶 `end_user`（問 Agent 擁有者）、有 `end_user` 沒部門（Gateway 資料缺陷，該修）。 |
| 2. 失敗與重試浪費 | 浪費 | 照字面：每個請求只留最後一次成功，其他嘗試的費用與 token 都算浪費。依成因分兩行：最後有成功的是**重試浪費**（重試策略太積極），從未成功的是**純失敗浪費**（上游壞了）。失敗與 timeout 照樣依 token 計費。 |
| 3. 重試風暴 | 異常偵測 | 同一 `request_id` 在任一 60 秒內有 3 次以上嘗試。先依 `ts` 排序，多台 Gateway 合併造成的亂序不影響結果。 |
| 3. 錯誤率 > 20% | 異常偵測 | 檢查**所有可能的** 5 分鐘窗，不是對齊時鐘的固定格，也不只是以記錄為結尾的窗，並列出最高的那個窗與時間範圍。樣本少於 20 的 key 不擋掉，另外列在「低樣本」區（見假設）。 |
| 4. P50 / P95 延遲 | 各模型延遲 | 只算成功的嘗試，nearest-rank 不內插，不列平均值（LLM 延遲長尾重，平均值會誤導）。 |

設計原則是**寧可吵，也不要安靜地給錯的數字**：壞掉的行、缺欄位、未定價的模型都會被計數並在報表末尾說明，不會悄悄變成 0。

## 結果可信嗎

`generate.py` 的背景流量由隨機種子決定，下面這些病徵則一律固定注入，換種子也一定出現。對照報表就能確認每一項都有被抓到：

| 注入的病徵 | 報表上的結果 |
|---|---|
| 60% 直接呼叫 | 無法歸屬約 60% |
| 沒帶 `end_user` 的 Agent 批次工作、20 個沒部門的 `end_user` | 無法歸屬的第二、三類 |
| 重試後成功、三次都失敗、串流中途 timeout | 重試浪費、純失敗浪費 |
| 14 秒內 4 次嘗試 | 重試風暴 `req-storm-000` |
| 跨 14:15 的事故（固定 5 分鐘格各只有約 18%） | 錯誤率異常 `key-incident` 36% |
| 低流量 key 上的連續失敗（`key-prod-1`、`key-data-1`、`key-eng-2`） | 低樣本區前三名 |
| 3 次呼叫錯 1 次的排程 key（誘餌） | 低樣本區，排在真事故後面 |
| 同一請求成功兩次、2 行壞資料、1 個未定價模型 | 對應的警告 |

## 假設

| 項目 | 值 | 來源 |
|---|---|---|
| 一天筆數 | 15 萬 | 題一推算：450 萬/月 ÷ 30 |
| 基準錯誤率 | 0.5% | 題一推算：成功率 SLO ≥ 99.5% |
| prompt / completion token | 平均 3,000（P95 12,000）/ 500 | 題二給定 |
| 直接呼叫佔比 | 60% | 純假設，情境只說「員工也直接呼叫」 |
| 雲端模型單價 | 見 `config.toml` | 廠商官方定價，2026-11-07 快照，出處見 [`docs/research/llm-token-pricing.md`](docs/research/llm-token-pricing.md) |
| 地端模型單價 | 0.25 / 2.00 USD 每百萬 token | 推導：H100 時租 ÷ 吞吐量，只準到數量級 |
| 錯誤率樣本門檻 | 20 | 見下 |

- **為什麼要分「低樣本」區**：基準錯誤率 0.5% 時，5 分鐘只有 3 次呼叫的健康 key，錯 1 次（33%）的機率約 1.5%，每天約 4 次誤報；有 20 次呼叫的 key 要錯 5 次才超過 20%，約 200 年一次。混在一起，真事故會被雜訊淹沒；直接擋掉，又會漏掉低流量 key 的真事故。所以照題目規則全部列出，但分兩區。
- **輸入**：欄位名稱照題目。`agent_id`、`end_user`、`end_user_dept` 沒有這個欄位、`null` 或空字串都視為空；沒有時區的 `ts` 視為 UTC。
- **單價**：使用單一費率，沒有處理長 prompt 的分級計價和 prompt caching 折扣。目前 P95 只有 12,000 token，分級的影響很小。
- **延遲**：`latency_ms` 分不出首 token 時間與總耗時，所以無法驗證題一以首 token 定義的 SLO，需要 Gateway 另外記錄 `ttft_ms`。
- **報表預設不含員工識別碼**：部門分攤不需要知道是誰，逐人明細要用 `--include-users` 明確開啟。

## 每天 1,000 萬筆時

實測（MacBook，Python 3.14，單一行程）：

| 筆數 | 輸入 | 時間 | 峰值記憶體 |
|---|---|---|---|
| 15 萬（目前一天） | 49 MB | 0.9 秒 | 117 MB |
| 100 萬 | 325 MB | 6.8 秒 | 660 MB |
| 1,000 萬 | 3.3 GB | 103 秒 | 3.8 GB |

**先撐不住的地方**
- **記憶體**：每次嘗試都留在記憶體裡（依請求、依 key、依模型各一份），用量跟筆數成正比。一天 3.8 GB，2 GB 的容器就跑不完，一次重算一個月更不可能。
- **時效**：這是每天跑一次的批次。錯誤率飆高要在幾分鐘內處理，隔天才在報表上看到已經沒用。

**怎麼改**
- 錯誤率告警移到 Gateway：每把 key 維護 5 分鐘的計數器（或輸出 Prometheus 指標加告警規則），幾分鐘內就能通知。每日報表留作事後檢討。
- 報表改成 Gateway 每小時寫 Parquet，用 DuckDB 查詢：單一行程、不用維運叢集、記憶體不夠時會用磁碟，浪費、風暴、錯誤率都能用 window function 寫。6 人團隊維護得起。
- 如果留在 Python：三種計算需要的排列方式不同，要分開處理。浪費與風暴依 `request_id` 雜湊分片，錯誤率依 key 分組，延遲改用直方圖（P95 變成誤差有上限的近似值）。

**改了之後什麼變難**
- 跨午夜的重試、跨檔案的 5 分鐘窗，切開的地方要多讀前一段資料，不然會算錯。
- 多台 Gateway 的記錄不會同時到齊，最近一小時的數字之後可能被重算改變。
- 即時告警與每日報表各算一次錯誤率，定義稍有不同就會出現「告警響了、報表沒有」，需要共用同一套規則與測試案例。
